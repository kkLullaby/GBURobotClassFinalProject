# 答辩 Demo 脚本

> 时长：**4 分钟 ±15 秒**  
> 主题：**Otto · 你的双向化身**（场景一 + 二的合成方案）  
> 适用场景：课程答辩 / 实验室 demo / 给朋友炫耀

---

## 现场布置

| 位置 | 物品 |
|------|------|
| 讲台 | 笔记本（开着 Hermes TUI）+ 大屏投影笔记本桌面 |
| 评委席前方 | Otto 机器人（USB 供电 + WiFi 接热点）|
| 你身上 | 手机（开 Telegram，登录 Hermes Bot） |
| 后台 | 备用：USB 数据线、移动电源、提前录好的 5 段演示视频（fallback） |

### 提前准备清单（演示前 1 小时）

- [ ] ESP32 烧录已是最新固件
- [ ] xinnan-tech server 已起，日志窗口可见
- [ ] Hermes Agent 在 TUI 窗口运行
- [ ] openai-shim FastAPI 在另一窗口运行
- [ ] xiaozhi-mcp-adapter 注册到 Hermes 成功（启动日志看 `mcp_servers: xiaozhi loaded 7 tools`）
- [ ] 手机 Telegram 跟 Hermes Bot 已连通（手动发"ping"，机器人有回应）
- [ ] 投影分屏：**左侧 Hermes TUI / 右侧 xinnan-tech server 日志**
- [ ] WiFi 热点已开，机器人已连入
- [ ] 把测试时积累的"今天的早安清单"塞进 cron 准备好

### 暖场（开始前 30 秒）

> "大家好，我演示的是基于 ESP32 小智机器人 + Hermes Agent 的合作项目。**关键词：把一个开源 AI 助手，给了一具身体。**"
>
> "为了说明它能做什么，我准备了一段 4 分钟的演示，分四段，包括一段我**不会直接说话**的部分。"

## 第 1 段 · 「早安时间」（45 秒）

**目的**：建立 ambient awareness 概念 —— 机器人不只是被动应答，能主动表达。

**舞台动作**：你站讲台旁，按一下笔记本空格键（触发预置 cron 任务）。

### 时序表

| 时间 | 你 | 机器人 | 大屏发生 |
|------|----|------|--------|
| 0:00 | (空格触发) | 屏幕从睡眠 → 笑脸，转头朝你 | TUI 弹出 cron 触发日志 |
| 0:05 | (站立) | "早，今天周二，你 GitHub 上有 2 个 PR 等 review，下午 3 点和导师有约" | xinnan-tech log 显示 TTS 流 |
| 0:18 | "把第一个念给我听" | "好的，PR #58，标题《优化 xiaozhi MCP adapter》，alice 提的，主要改动是……" | TUI 显示 `tool_call: gh_pr_diff(58)` |
| 0:40 | "好，等会处理" | (笑脸，回归 idle) | TUI 显示 `intent: defer` |

### 旁白（机器人念完后说给评委）

> "这是 cron 触发的 ambient mode。Hermes 每天 9 点扫我的 git 仓库、日历、未读邮件，**通过 MCP 调机器人 speak 工具**主动播报。机器人不需要被问 —— 它知道今天该说什么。"

### Fallback

- 如果 cron 触发失败 → 在 TUI 里手动打 `/cron run morning_briefing`
- 如果 LLM 慢 → 跳过 0:18 那轮，直接进第 2 段

---

## 第 2 段 · 「社交守门员」（50 秒）

**目的**：演示**跨 channel routing** —— Hermes 把 Telegram channel 收到的消息按规则分级转给机器人。

**舞台动作**：你假装去开桌面别的程序，眼睛不在机器人上。

### 时序表

| 时间 | 触发 | 机器人 | 大屏 |
|------|------|------|------|
| 0:45 | 你**手动**用副手机 / 助手发 Telegram 给 Hermes Bot："周末加班，能来吗？老板" | 红光闪烁 + 转头朝你："⚠️ **老板找你，紧急**" | TUI 显示 `[Telegram] 老板: 周末加班...` → `routing: priority=urgent → xiaozhi` |
| 1:00 | "念出来" | "周末加班，能来吗？" | `tool: speak()` |
| 1:08 | "回他：可以，明天 9 点到" | "已回复" + 屏幕 ✓ | TUI 显示 `tool: send_message_tool(platform=telegram, ...)` |
| 1:18 | (你**手动**触发另一条 Telegram："要不要去吃火锅 -tom") | 屏幕轻闪蓝色，**不打扰**，角落小红点 | TUI 显示 `routing: priority=normal → silent notify` |

### 旁白

> "Hermes 的 routing rule 是用**自然语言**写在它的 system prompt 里的：'**老板/家人来消息要朗读；普通朋友只视觉提示**'。这意味着我**不写代码**就能改优先级 —— 比传统智能音箱的硬编码灵活很多。"
>
> "另外这条回复实际上是机器人**通过 send_message_tool 把消息推回 Telegram channel** —— 一条消息从 Telegram 进来，从 xiaozhi 朗读，又回到 Telegram —— 三个 channel 协作。"

### Fallback

- Telegram 国内不稳 → 改用 webhook channel（你提前写个 curl 触发）
- 优先级判定失败 → 演示词改为"虽然这条没念出来，但 TUI 显示已收到，说明系统在工作"

## 第 3 段 · 「远程驾驶」（90 秒）—— **🎬 答辩高光**

**目的**：物理化身的"远程操控"价值。**你不说话，但通过手机让机器人在评委面前完整应答。**

**舞台动作**：

> "现在最有意思的部分。我把机器人留在这里 (指向评委桌上的 Otto)，**我退到教室门口**。"
>
> (你走到门口，掏出手机)
>
> "**接下来 90 秒，我手机以外的所有声音都来自机器人。**"

### 时序表（你只在手机 Telegram 输入文字）

| 时间 | 你（手机 Telegram → Hermes Bot） | 机器人在评委面前 | 评委 |
|------|-----|------|------|
| 1:35 | "robot, 简单介绍一下你自己" | (面朝评委) "大家好，我是 Otto，一个基于 ESP32-S3 的桌面机器人，跑着上游 78/xiaozhi-esp32 固件……" |  |
| 2:00 | "如果有人想问问题，告诉我" | 屏幕显示 🎤 listening 模式 + 红色 LED 提示在录音 | (观察) |
| 2:15 | (TUI 收到 push："评委 A 问：**这个延迟大概多少？**") | 屏幕显示字幕："评委: 这个延迟大概多少？" | 评委 A 真问了 |
| 2:30 | "答：端到端 2-3 秒，主要瓶颈在 ASR 和 LLM provider，本地模型能压到 1.5 秒以内" | (面朝评委) "端到端 2 到 3 秒，主要瓶颈在……" |  |
| 2:55 | "显示我项目地址的二维码" | 屏幕显示 GitHub 二维码 | (评委可扫) |
| 3:05 | (你走回讲台) | 屏幕恢复笑脸，转头朝你 |  |

### 旁白（这段结束后立刻说）

> "**注意一件事**：刚才那 90 秒，我**没对评委说一句话**。但我用机器人完成了：自我介绍、听评委提问、转写并 push 到我手机、合成回答、显示二维码。"
>
> "技术上，这是 Hermes 的**多 channel 投递**：Telegram channel 是我的输入，xiaozhi channel 是输出。**对我而言是一段对话，对评委而言是一个会说话的机器人。**"

### 隐私必加（这段必须显式讲，否则掉分）

> "你们看到红色 LED 一直亮，那是 listen_ambient 工具触发的**明示告知**。 Hermes 系统 prompt 里写了规则：**未经显示授权不允许调用 listen_ambient**，而且每次必须亮指示灯。这一点是我专门写到隐私边界设计里的。"

### Fallback

- **🔥 最高风险段**。如果任何一步失败：立刻退场，"接下来我用提前录制的版本展示"，播放预录视频
- 准备好 5 段独立的视频片段（每段 15 秒），可以从任何中断点续接
- ASR 慢 → 准备好"我刚才让她答的内容是 ..." 的口头讲解，免得现场尬

## 第 4 段 · 「架构 + 总结」（55 秒）

**目的**：让评委看懂"创新点在哪、为什么不是把零件拼起来"。

**舞台动作**：切到提前准备好的架构图 slide。

### 旁白脚本（背下来，不要看稿）

> "刚才你们看到的，背后是这样的架构（指图）：
>
> 1. **下层** 是 ESP32 上的小智固件，**完全用上游原版，零修改**；
> 2. **中层** 是 xinnan-tech 的开源 xiaozhi server，**Docker 一行起来**；
> 3. **上层** 是 NousResearch 的 Hermes Agent，**多 channel 通用 AI 助手**；
> 4. **我写的是中间两个胶水**：
>    - **`xiaozhi-mcp-adapter`** —— 把 ESP32 暴露的 MCP 工具翻译给 Hermes
>    - **`openai-shim`** —— 让 xinnan-tech server 把对话流推给 Hermes session
>    - **`Hermes xiaozhi channel plugin`** —— 让 Hermes 把机器人当作 Telegram 一样的标准 channel
>
> **创新点不在硬件，在拓扑**：
>
> - 把一个**仅活在终端和聊天软件里**的开源 AI 助手 **物理化身**为一具能说话、能转头、能感知环境的机器人；
> - 我**没造任何私有协议** —— 全程用 MCP 标准 + Hermes 标准 channel 接口；
> - **架构是后端无关的**（演示用 DeepSeek，可以无缝换 Ollama / Anthropic / OpenAI）；
> - 我会把这套 xiaozhi channel 作为 PR 提交到 Hermes 社区，可能成为它**第一个 ESP32 embodiment**。
>
> 谢谢。"

### Fallback

- 时间不够 → 跳过中间架构细节，只说"创新点不在硬件，在拓扑"那一句
- 时间富裕 → 提一句"未来想做 cross-channel session 桥接，Hermes 目前还不支持，这是社区可贡献方向"

## 评委可能问的 8 个问题 + 准备答案

| Q | A 要点 |
|---|--------|
| 1. 跟智能音箱（小爱、Alexa）有什么不同？ | 智能音箱**封闭、单端**；这个**开源、多 channel、可换大脑** —— 同一个机器人能被我手机、电脑、Telegram 控制 |
| 2. 没有 GPU 能跑吗？ | 服务端**无 GPU 也能跑**，LLM 用云端 API；如果要本地化，Ollama 跑 7B 模型在 16GB 显存够 |
| 3. 隐私怎么保证？ | 三条：(a) `listen_ambient` 强制 LED 提示；(b) 默认 LLM 后端走云不存数据；(c) 想完全本地就换 Ollama，全程不出本机 |
| 4. xiaozhi 自家云服务和你这个有什么本质区别？ | 自家云锁定虾哥的 LLM 和工具集；我这套**让任何 Hermes 工具/MCP server 都能驱动机器人**，工具生态量级不同 |
| 5. ESP32 这么弱能跑这么复杂的栈吗？ | 弱在算力 —— **算力在电脑**，ESP32 只做**音频采集 + 命令执行**，分工合理 |
| 6. 为什么不用 Claude Code？ | Claude Code 闭源、单 channel、绑定 Claude 模型；Hermes **开源 MIT、20+ channel、后端无关**，更适合"通用化身"定位 |
| 7. 离线场景能用吗？ | LLM 部分需要后端（本地 Ollama 也算），网络断了就退化为离线唤醒 + 预设回复 |
| 8. 这玩意儿有商业价值吗？ | 不是直接商业化方向，但**架构本身**可借鉴 —— 任何 IoT 设备想接 AI 助手生态都可以套这个 pattern |
